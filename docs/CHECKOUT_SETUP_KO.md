# DMXDT 결제·주문 운영 전 점검 (2026-11-03)

## 반영 범위

- 기존 화면 디자인 유지
- 실서버의 결제 설정과 주문 DB가 준비되지 않으면 결제 버튼 차단
- 상품·수량·호수·주문자 이름·전화번호·이메일·우편번호·주소·배송메모를 서버에서 검증하고 결제 **전에** 저장
- 토스페이먼츠 승인 결과의 주문번호·결제키·금액을 기존 주문과 대조하고 서버에 저장
- 결제 승인 API에 멱등키 추가, 반복 승인 시 최초 주문 내역 반환
- 결제 완료와 가상계좌 입금 대기 구분; 상태 미확인 시 무턱대고 재결제하지 않도록 경고

## 운영 전 반드시 진행할 단계

1. Supabase 프로젝트를 만든 뒤 SQL Editor에서 \`supabase/schema.sql\`을 실행합니다.
2. Vercel 프로젝트의 **서버 측** 환경변수에 \`SUPABASE_URL\`, \`SUPABASE_SERVICE_ROLE_KEY\`,
   \`TOSS_PAYMENTS_SECRET_KEY\`를 설정합니다. \`NEXT_PUBLIC_TOSS_PAYMENTS_CLIENT_KEY\`에는 매칭되는 공개 클라이언트 키만 넣습니다.
3. 처음에는 **테스트 키**로 설정하고 \`PAYMENTS_ENABLED=true\`를 켭니다. 실제 운영 키로 바로 시험하지 마세요.
4. 주문서에서 테스트 결제하고 Supabase의 \`dmxdt_orders\` 테이블에
   고객 배송정보·상품·금액·\`paid\` 상태·\`payment_key\`가 저장되는지 확인합니다.
5. 재진입/새로고침에서 이중승인되지 않는지, 결제 중단 시 \`pending\`으로 남는지,
   주문금액 변조와 임의 주문번호가 거부되는지 점검합니다.
6. 가상계좌는 입금 완료 웹훅 및 검증 절차가 구축되기 전까지 토스페이먼츠 관리자에서 **사용 중지**하세요.
   이 수정은 최초 결제 승인 시 \`awaiting_deposit\` 기록까지만 지원합니다.
7. 실제 판매 전 **고객/회사 이메일·문자 자동 알림, 취소·환불 처리, 운영자 주문 관리,
   재고 연동, 정산·세금처리, 비밀번호 및 접근권한 점검**이 추가로 필요합니다.
8. 토스페이먼츠 계약/MID의 운영 승인, 결제수단, Vercel의 상업 운영 가능 플랜을 확인한 뒤
   실제 결제 테스트 금액·시간·취소 계획을 합의해 검증해야 합니다.

## 주의

- 이 브랜치는 결제 안전성과 주문 영구 저장의 **1차 보완**입니다. 완성형 쇼핑몰이 아닙니다.
- \`PAYMENTS_ENABLED\`가 false면 체크아웃 API는 새 주문 생성 및 결제 요청을 차단합니다.
  이미 인증된 결제의 상태 확인용 승인 API는 기존 거래 복구를 위해 독립적으로 동작합니다.
- 테스트 키와 운영 키를 섞으면 결제 승인이 실패합니다.
- 해당 SQL은 브라우저 역할의 DB 접근을 차단하며 주문 데이터는 서버 서비스 키로만 취급합니다.
- Supabase와 토스페이먼츠의 운영 키, 고객 개인정보를 GitHub 이슈·PR·로그에 넣지 마세요.
- 결제는 승인되었으나 DB 기록에 실패한 경우 주문번호로 토스페이먼츠 거래를 확인한 뒤 수동 복구해야 합니다.
  해당 상태에서는 고객에게 재결제를 요청하면 안 됩니다.
